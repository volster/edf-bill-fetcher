audit-pass-3: dispatcher/registry structural consistency tests

A paying client gets all PDF/DOCX report sections delivered in the
order they appear in REPORT_SECTIONS. That contract is enforced at
runtime by a RuntimeError ("REPORT_SECTIONS lists X but no builder
is wired") — but the runtime check fires only when the user
actually requests a section, not at code-review time or CI time.

This commit pins the parity invariant as a CI test so a future
contributor cannot add a section to REPORT_SECTIONS without
wiring both the PDF and DOCX dispatchers.

tests/test_dispatch_parity.py asserts:

- The PDF section_builders dispatcher exposes the same key set as
  REPORT_SECTIONS (per-file AST extraction).
- The DOCX section_builders dispatcher exposes the same key set as
  REPORT_SECTIONS.
- The two dispatchers agree on the key set (no PDF-only or
  DOCX-only sections).
- RenderContext() defaults to rendering all registry sections.
- RenderContext constructed with an unknown key does not raise —
  defensive contract for forward-compatible callers.
- generate_ombudsman_pdf / generate_ombudsman_docx are importable
  and callable (smoke check that the dispatcher modules have not
  been left half-rewritten).
